# Aura 1.0.0b13.1

A maintenance release of 1.0.0b13, from `maint/1.0.0b13`. It adds one fix (#213) and CI for maintenance branches.

- **NVMe on post-M4 Macs after a 1.0.0b11 or later Stage 1 (#213).** Since 1.0.0b11 (adf55805), a stage that used a post-M4 ANS powers it off and passes its SART entries on as `nvme.sart=`. An ESP Stage 2 that boots its embedded U-Boot never started ANS again. It only wrote the entries to the device tree as `apple,sart-entries`. The U-Boot that aura embeds adopts a running ANS and cannot start one from off, so it failed to probe NVMe (`Failed to probe 'nvme@3cdcc0000': err=-19`) and the boot stopped in U-Boot. Stage 2 now starts an ANS that arrived off with `nvme.sart=` and hands it on running to every payload, as the `boot=` path already did for Linux. This affects the M4 (T8132), M4 Pro and M4 Max (T6040, T6041), the MacBook Neo (T8140) and T6050. Without `nvme.sart=` nothing changes: M1 to M3, T8152, and every Stage 1 from 1.0.0b10 or earlier, which leaves ANS running for the next stage.
- **CI.** Build, format-check, test and stage1-size also run for `maint/` branches.

`VERSION` stays `1.0.0b13`, so the images are labelled `1.0.0b13-g<commit>`, as 1.0.0b12.1 was. The Stage 1 version parsers in the distributions' Stage 2 updaters read `<x.y.z>b<N>` with an optional `-g<commit>`. Distribution packages carry the version 1.0.0b13.1.

The 1.0.0b13 notes, and the 1.0.0b7 notes on the CTXR window, apply unchanged.

## Qualification

Both rows chain like a 1.0.0b11 or later Stage 1, without changing the installed Stage 1. aura-try loads the packaged 1.0.0b13 ESP Stage 2 with a `chainload=` line. That stage adopts Stage 1's running ANS, powers it off and chainloads the test Stage 2 with `nvme.sart=`. The test Stage 2 is the Mac's installed Stage 2 with its aura image replaced by #213's (aaec599f), keeping the installed device trees and U-Boot. Nothing was committed.
