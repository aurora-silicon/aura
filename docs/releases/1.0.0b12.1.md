# Aura 1.0.0b12.1

A maintenance release of 1.0.0b12, from `maint/1.0.0b12-secboot`. The default Stage 1 and the ESP Stage 2 are byte-identical to 1.0.0b12's, so a Mac boots the same code. What is new is in the tools and in the secure-flavour Stage 1, which now links with every distribution toolchain.

- **Secure-flavour Stage 1 (#200).** A `SECBOOT=audit SECBOOT_FLAVOUR=secure` Stage 1 from 1.0.0b12 did not link with Fedora's or nixpkgs' clang 22 ("Code and data reach the DCP log buffer after stage 1"). The secure flavour never offers a USB host the proxy, and now decides that at compile time, so the proxy, its USB windows and the hypervisor are left out of it. The J873g path, which ran the proxy unconditionally, boots its payload or reboots in the secure flavour. The default flavour is unchanged.
- **Boot objects for the CTXR window (#195).** `tools/macho_boot_object.py --execute-window` pads a Stage 1 boot object for the code-execute window that M4-generation and later chips require, as aurora-installer does, so a Stage 1 for those Macs can be built on Linux (`aurora-secboot stage1 build`).
- **Signing a Stage 2 (#197).** `tools/secboot_sign.py sign-image` refused every aura Stage 2, because aura's own code holds the `chosen.aurora,measure-` format string. It now searches only the payloads after the aura image. Reported by Bartosz Nitka.
- **CI.** `stage1-size.yml` reports the room every Stage 1 flavour has left with each distribution toolchain (#200). `maint-identity.yml` builds the default images of a maintenance branch and of the release it maintains with each toolchain and fails unless they are byte-identical. Build, format-check, test and stage1-size also run on `maint/` branches.

`VERSION` stays `1.0.0b12`, so the images are labelled `1.0.0b12-g<commit>`. The Stage 1 version parsers in the distributions' Stage 2 updaters read `<x.y.z>b<N>` with an optional `-g<commit>`, and a Stage 1 built from this tree, for example by `aurora-secboot stage1 build`, keeps a label they accept. Distribution packages carry the version 1.0.0b12.1.

The 1.0.0b12 notes, and the 1.0.0b7 notes on the CTXR window, apply unchanged.

## Qualification

No hardware trial: the images a Mac boots by default are 1.0.0b12's.

Default images of this release and of `v1.0.0b12` (ea20cedb), built with the same version label (`AURA_VERSION_TAG`) and each distribution's toolchain and flags (`RELEASE=1 CHAINLOADING=1 USE_CLANG=1 BUILTIN_LOGO=aurora`, plus `BUILDSTD=1` on Fedora; `ESP_STAGE2=1` for Stage 2):

| --- | --- | --- | --- | --- |

Hashes are sha256 prefixes with the label `identity` (`maint-identity.yml`). The same check by hand with Fedora 44's toolchain and the label 1.0.0b12 packages carry (`1.0.0b12-gea20cedb`) also gives identical images.

A package build labels this release `1.0.0b12-g<commit>`, so its images are not byte-identical to a 1.0.0b12 package: the label sits in three strings, and the linker's merged strings take a different order, which moves string addresses in `.rodata` and in the code that loads them. Built that way with Fedora 44's toolchain, only `main.o`, `payload.o`, `usb_dwc3_hs.o` and `usb_dwc3_ss.o` (the objects holding the label) differ once debug info is stripped, every section has the same address and size, and every function in `.init` and `.text` is the same instruction sequence, with each relocated operand naming the same symbol or the same string bytes.

The secure-flavour Stage 1 links with every toolchain and keeps at least 12 KiB of headroom (`stage1-size.yml`; secure audit, bytes): gcc 84592, Fedora 12944, Arch Linux ARM 13064, nixos-aurora 12820, Homebrew clang 13064.

CI on the release head: build (gcc), stage1-clang, format-check, test, stage1-size and maint-identity.
