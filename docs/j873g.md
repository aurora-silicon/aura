# J873g / T8152 initial bring-up

This port targets the M6 Mac mini identified by `J873g`, `Mac18,5`, chip
`0x8152`, board `0x24`. It provides a proxy using the firmware's
DockChannel/KIS console, architectural MMU/cache setup and inherited framebuffer.
It boots an appended payload or `boot=` from storage, or runs the proxy.

The measured MIDR parts are `0x072` (E cores) and `0x073` (P and M cores).
They do not inherit M4 fast-IPI or implementation-defined CPU tuning. PMGR2
and DCP reinitialization remain outside this port.

Native SMP starts all twelve CPUs on explicit request using the PMGR2 CPU-release
map. See [SMP qualification](j873g-smp.md) for the supported dispatch path and
reset requirements.

## Failure cases and end-to-end qualification

Before changing this path, account for a mismatched board, an incorrect console
channel, watchdog resets, unsupported Apple system registers, MMU/cache faults,
an inherited framebuffer outside ordinary RAM, accidental legacy PMGR writes,
and a chainload over active secondary CPUs. A build alone cannot exclude these.

Build with `make -j8` using the documented AArch64 toolchain. Preserve the installed
recovery image. From a fresh single-CPU m1n1 recovery session, verify the complete
target identity, hash the candidate binary, transfer it to RAM and verify its
readback before chainloading. Never chainload over running secondary CPUs.

Capture the build ID and `J873g: KIS bring-up with native SMP` banner, then verify proxy
NOP, boot arguments, the live ADT identity, an allocated RAM write/readback and
architectural counter progress. Save the console log, exact source commit,
binary SHA-256 and a machine-readable receipt. Reboot into the preserved recovery
image on failure; identify the host USB port afresh before any reset.

Linux handoff qualification is separate from the native SMP checks.

## Booting Linux

Before the proxy starts or a payload boots, `j873g_run_proxy()` does what the
J873 Linux device trees expect the loader to have done (`src/j873.c`; the
Linux side documents the same steps in `tools/aurora/j873/loader`):

- USB2 host on usb-drd1 (back-left) and usb-drd2 (front, VL822 hub): power
  the controllers and put their eUSB2 PHYs into host mode with both DARTs
  left disabled, wake the back-left port controller (hpm1, SSPS 0) and
  release the hub reset (nub-gpio 0x27).
- N1 Wi-Fi/Bluetooth: write the SMC pcIO function-reset level 0, then 1.
- Internal PCIe: apply the PHY tunables, ungate the AUS5 PHY, write the ADT
  lane-cfg and apply the apcie0/apcie2 DART tunables while those DARTs are
  unused.

Each step checks iBoot's state first and leaves anything it does not
recognise alone; a controller already set up is skipped.

A payload appended to the image (kernel, device tree, initramfs, and
`chosen.bootargs=`), or `boot=` from the EFI system partition, then boots
directly; `aura-proxy` in the boot arguments keeps the proxy instead. The
T8152 device tree preparation keeps the usual reservations (devicetree, this
image, the retained heap with the DCP and ANS buffers, the CTRR area), fills
/chosen, the CPUs' spin-table release addresses, the MAC addresses, the HDMI
framebuffer as a second simple-framebuffer, and memory, and appends only
`arm64.nowfxt` to the boot arguments. There is no clock, USB, PCIe or DAPF
setup in the handoff.

NVMe uses the ADT `nvme-secure-reg-layout`: NVMe and NVMMU share reg[3], the
queues are set up as on M4 and the queue registers sit 0x4000 higher, with
LINEAR_SQ_CTRL at 0x2813c (pull request "nvme: T8152 secure register layout").
